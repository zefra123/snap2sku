# Bug 诊断：小程序图片上传报 `E_UPSTREAM: 图片上传失败`

- **报告日期**：2026-10-27
- **症状来源**：微信开发者工具控制台日志（`127.0.0.1-1793086704263.log`）
- **环境**：微信开发者工具 / WeChatLib 3.17.4，小程序端 uni-app + Vue3，服务端 Nuxt 4 dev server
- **当前状态**：✅ 已恢复可用，并已落地防复发措施（见第五节）

---

## 一、症状

日志中唯一的有效报错：

```
[snap2sku-debug] 图片识别流程异常 调用 uni.uploadFile
  Error: E_UPSTREAM: 图片上传失败，请检查网络后重试
    at fail (index.js:1)
```

对应代码位置：`apps/mp/src/pages/index/index.vue:186`，`uni.uploadFile` 的 **fail 回调**。

同时日志里还有一条容易误读的信息：

```
工具未校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书。
```

这是开发者工具「不校验合法域名」开关的**正常提示**，与本次故障无关，可以排除。

## 二、关键判定：`fail` 与 `success` 是两类完全不同的失败

这一点决定了整个排查方向，必须说清楚：

| 回调      | 触发条件                                                    | 本次是否属于此类 |
| --------- | ----------------------------------------------------------- | ---------------- |
| `success` | 收到 HTTP 响应（含 4xx / 5xx），由业务代码判断 `statusCode` | ❌ 否            |
| `fail`    | **网络层失败**：连不上、被拒绝、超时、域名不合法            | ✅ 是            |

看源码也印证了这一点（`index.vue:170-186`）：鉴权失败、图片超限（413）、格式错误（415）这些都会进 `success`，再交给 `apiErrorMessage()` 转成业务文案。既然走的是 `fail`，就说明**请求根本没到达服务端**，所有围绕"接口参数对不对""图片太大不大"的猜测都可以先放一边。

## 三、证据链

### 1. 小程序配置本身没错

`apps/mp/.env.local`：`VITE_API_BASE_URL=http://192.168.2.21:3000`

本机网卡 IPv4 实测只有两个地址：

```
192.168.2.21
127.0.0.1
```

局域网 IP 没漂（DHCP 换网段是同类问题最常见的原因，这次不是）。

### 2. 故障时刻：局域网地址上没人在听

```
TCP    127.0.0.1:3000         0.0.0.0:0              LISTENING       36852
```

注意是 `127.0.0.1:3000` 而不是 `0.0.0.0:3000`——服务**只绑了回环地址**。于是：

| 目标地址                              | HTTP 状态码         |
| ------------------------------------- | ------------------- |
| `http://127.0.0.1:3000/api/health`    | 200                 |
| `http://192.168.2.21:3000/api/health` | **000（连接失败）** |

000 就是 `uni.uploadFile` 走 `fail` 的直接原因。

### 3. 后来变好了：因为监听方式变了

同一台机器上再次检查，监听者已经换了个进程，且绑定方式不同：

```
TCP    0.0.0.0:3000           0.0.0.0:0              LISTENING       36548
```

此时复测：

| 目标地址                                   | HTTP 状态码                         |
| ------------------------------------------ | ----------------------------------- |
| `http://127.0.0.1:3000/api/health`         | 200                                 |
| `http://192.168.2.21:3000/api/health`      | **200**                             |
| `POST http://192.168.2.21:3000/api/upload` | **415**（业务错误，说明请求已到达） |

415 是因为测试时传了假字节流，但**它证明请求已经打到服务端并被业务代码处理了**——网络层通了。

### 4. 因果验证：绑定地址决定可达性

用一个临时 Node 服务做对照（跑完即删，未落任何项目文件）：

```js
srv.listen(3200, host); // host 分别取 127.0.0.1 和 0.0.0.0
```

| 绑定方式    | `127.0.0.1:3200` | `192.168.2.21:3200` |
| ----------- | ---------------- | ------------------- |
| `127.0.0.1` | 200              | **000**             |
| `0.0.0.0`   | 200              | **200**             |

结论可靠：**绑定回环 → 局域网地址不可达；绑定 0.0.0.0 → 可达，且本机没有被防火墙拦截。**

> 诚实记录一次过程失误：第一次做这个对照实验时，两组都返回了 000，属于**我自己脚本的假阴性**（同一端口连续启动两个服务，前一个尚未释放导致复用异常）。改成单进程、干净端口重跑后结果如上。第一次的 000 **不是**真实结论。

## 四、假设与验证结果

| #   | 假设                                         | 验证方式                                      | 结论                                                          |
| --- | -------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------- |
| H1  | 服务只监听 `127.0.0.1`，局域网地址无进程响应 | `netstat` + `curl` 对照                       | ✅ **成立，即根因**                                           |
| H2  | Windows 防火墙拦截入站 3000                  | 对照实验里 `0.0.0.0` 绑定后本机访问通         | ❌ 本机不成立；但**真机（另一台设备）仍需另行确认**，见第七节 |
| H3  | 本机 LAN IP 变了（DHCP 漂移）                | node 读网卡列表 vs `.env.local`               | ❌ 否，一致                                                   |
| H4  | 服务没起 / 已崩溃                            | `127.0.0.1:3000` 返回 200                     | ❌ 服务正常                                                   |
| H5  | 图片过大导致上传超时                         | fail 属网络层，且同期 `health` 就不通         | ❌ 否                                                         |
| H6  | 开发者工具 Agent 设置导致请求走代理          | 开发者工具对 `http://` 直连；且绑定修复后即通 | ❌ 本机不成立                                                 |

## 五、已落地的防复发措施

`pnpm dev` 默认只绑回环，这是 Nuxt 的保守默认行为，本身合理（不要让开发机上的 SSR 进程默认暴露到局域网）。但需要真机联调时必须显式放开。

查 `nuxt dev --help` 得到官方口径：

```
-h, --host    Host to listen on (default: NUXT_HOST || NITRO_HOST || HOST || nuxtOptions.devServer?.host)
--public      Listen to all network interfaces
```

因此在 `apps/web/package.json` 新增脚本：

```json
"dev:lan": "nuxt dev --public"
```

用法：

```bash
pnpm --filter web dev:lan
```

**`dev` 保持默认不变**，避免开发服务器默认对局域网开放；需要联调时用 `dev:lan` 显式开启。

## 六、一键复现回路（以后再出问题先跑这个）

```bash
# 注意 --noproxy '*' 不能省，理由见下方"血泪教训"
curl -s -o /dev/null -w "%{http_code}\n" --noproxy '*' --max-time 5 \
  http://192.168.2.21:3000/api/health
```

- 输出 `200` → 网络层没问题，去查业务层（鉴权、参数、图片格式）
- 输出 `000` → 网络层不通，按下面三步定位：

```bash
netstat -ano | grep ":3000"                 # 看监听地址是 127.0.0.1 还是 0.0.0.0
node -e "console.log(Object.values(require('os').networkInterfaces()).flat().filter(i=>i.family==='IPv4').map(i=>i.address).join('\n'))"
cat apps/mp/.env.local                      # VITE_API_BASE_URL 是否等于上面的局域网 IP
```

**血泪教训：不要相信本机 curl 的默认行为。** 这台机器的 shell 里有 `HTTP_PROXY=http://127.0.0.1:26177`，不加 `--noproxy '*'` 时，请求会先发给代理，代理连不上就返回 **502**——一个看起来像"服务挂了"的假状态码。本次诊断一开始就踩到它，差点得出完全错误的结论。

小程序那边配套的一种记录：把这条回路写成一个可重复执行的脚本，省得每次现敲。

## 七、待办（需要依次处理）

### 1. 真机预览还需确认防火墙（重要）

本节结论仅覆盖了「本机访问自己的局域网 IP」。**换成手机访问是另一条路径**，会真正经过 Windows 防火墙的入站规则。首次用于真机时请验证：

```bash
# 手机上浏览器访问，或本机用另一台设备 ping
http://192.168.2.21:3000/api/health        # 期望 {"status":"ok"} 或 200
```

若不通：Windows Defender 防火墙 → 入站规则 → 放行 TCP 3000（建议只对**专用网络**放行，不要对公用网络放行）。

另注：`.env.production` 里写的是 `https://snap2sku.icu`，那条线依赖域名备案与 HTTPS 证书，与本机的 5000/3000 联调无关，**备案号下来之前不要去碰域名解析**。

### 2. 建议一起改掉：错误信息被吞（等 Codex 交付后合并）

`fail: () => reject(...)` 把系统提供的 `errMsg` 整个丢弃了，导致日志里只剩一句没有信息量的话，逼得这次要靠 `netstat` 做考古。这在小程序端共有 **3 处**：

| 位置                                    | 现状                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| `apps/mp/src/pages/index/index.vue:185` | `fail: () => reject(new Error("E_UPSTREAM: 图片上传失败，请检查网络后重试"))` |
| `apps/mp/src/pages/index/index.vue:303` | 同上模式                                                                      |
| `apps/mp/src/api.ts:120`                | `fail: () => reject(new Error("E_UPSTREAM: 请求失败，请检查网络和服务地址"))` |

建议改法（以 `api.ts:120` 为例）：

```ts
fail: (error) =>
  reject(
    new Error(
      `E_UPSTREAM: 请求失败（${error?.errMsg ?? "网络不可用"}），请检查服务地址是否可达`,
    ),
  ),
```

这样以后日志里会直接出现 `url not in domain list` / `request:fail timeout` 这类决定性线索，不需要猜。

**本次没有直接改这些文件**，因为工作区里存在 Codex 尚未提交的改动（`api.ts`、`pages.json`、`AGENTS.md`、`pages/detail`、`pages/records`、`static/tab` 等），贸然改同一批文件会和它的产出冲突。建议等它交付提交后再合并这块小改动。

## 八、复盘：是什么让这个 bug 难查

1. **`fail` 回调丢弃了 `errMsg`** —— 把"连不上"和"请求失败"混成一模一样的文案，信息在这一层就丢了。这是最大的问题。
2. **本机代理让 curl 说了假话** —— 返回 502 伪装成服务端错误，实际上请求压根没出去。
3. **监听绑定地址不可见于任何 UI** —— `pnpm dev` 起完不会告诉你是回环还是 0.0.0.0，只能靠肉眼读 `netstat`。
4. **`--public` 这个官方开关是存在的，但没人知道** —— 于是默认配置只能连回环，联调全靠"碰巧"。第五节的脚本解决了这一条。
