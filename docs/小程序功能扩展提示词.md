## 要接的三个接口（后端现成）

| 方法 | 路径                                 | 用途                                            |
| ---- | ------------------------------------ | ----------------------------------------------- |
| GET  | `/api/records`                       | 记录列表，返回 `ProductRecordWithImageUrls[]`   |
| PUT  | `/api/records/:id`                   | 编辑记录，返回单个 `ProductRecordWithImageUrls` |
| POST | `/api/records/:id/describe`          | 生成卖货描述（SSE）                             |

所有写请求必须带请求头 `x-access-code`，值从 `uni.getStorageSync("snap2sku-access-code")` 读取，沿用 `apps/mp/src/api.ts` 里已有的 `buildAccessHeaders()`，**不要另写一套访问码逻辑**。

## 已知坑（这几个不处理一定返工）

**坑 1：解析列表数据会静默丢掉图片地址。**
`apps/mp/src/api.ts` 里的 `parseProductRecord()` 用的是 `ProductRecordSchema`，而这个 schema **没有 `.strict()`**，zod 默认是 strip 模式——用它解析列表数据，`imageUrls` 字段会被**静默丢弃**，列表页将拿不到任何图片。

必须用 `packages/shared` 已导出的 `ProductRecordWithImageUrlsSchema` 来解析列表与详情的返回，推荐在 `api.ts` 里新增：

```ts
export function parseProductRecordList(
  value: unknown,
): ProductRecordWithImageUrls[] {
  const parsed = z
    .array(ProductRecordWithImageUrlsSchema)
    .safeParse(value, { jitless: true });
  if (!parsed.success) throw new Error("E_VALIDATION: 记录列表格式不正确");
  return parsed.data;
}
```

注意 `api.ts` 既有代码用的是 `jitless: true`，保持一致。

**坑 2：SSE 事件名是 `generated` / `done` / `error`。**
旧代码里的 `result` 事件**已被重命名废弃**。两个描述接口都是 SSE 流式返回。`uni.request` 需要开 `enableChunked` 才能分片接收；**如果你的 uni-app 版本下小程序不支持 `enableChunked`，就退化为一次性接收完整响应**，并在 UI 上给明确的等待态（至少要有 loading 文案和禁用重复点击的整体遮罩），不要假装流式。

**坑 3：页面跳转只传 `id`。**
`uni.navigateTo` 的 url 有长度限制，绝对不要把整个 record 对象序列化后塞进 url。详情页接收 id 后自行取数据。详情页的数据源建议用列表已拉到的数据兜底，`PUT` 成功后再用返回值回写，不要为了单条详情再去加一个 `GET /api/records/:id` 接口。

**坑 4：签名图片 URL 有时效但不用担心。**
`imageUrls` 是形如 `/api/uploads/xxx?exp=...&sig=...` 的签名地址，60 秒过期。但 `GET /api/records` 每次返回都重新签发，**所以列表页每次下拉刷新就能拿到新地址**，不必缓存旧 URL。

**坑 5：新增页面要同步改 `apps/mp/src/pages.json`。**
加 tabBar 还需要图标资源，图标必须放在 `apps/mp/src/static/` 下，不能用远程地址。

## AGENTS.md 里与本任务直接相关的硬约束

这几条最容易踩，**违反了会被直接打回重写**：

1. **禁止装任何新依赖**（§5）：不要引入 Tailwind、任何 CSS 框架、Pinia、ORM。如需新增运行时依赖必须先问。
2. **设计 token 唯一来源**（§4.2）：组件里**禁止写死颜色、字号、圆角**。小程序端的设计 token 在 `apps/mp/src/styles/tokens.wxss`（由 `pnpm --filter mp gen:tokens` 从 `apps/web/app/assets/css/tokens.css` 生成），样式一律引用 token 变量。
3. **字段名固定**（§8）：
   - SKU 价格字段只能是 `tagPrice`（吊牌价）和 `wholesalePrice`（批发价），**禁止出现 `listPrice` / `salePrice`**（PRD 已废弃的旧命名）。
   - 多平台文案字段固定为 `descriptionVariantsAi`，平台 key 固定 `douyin` / `xiaohongshu` / `shipinhao`，**禁止自创 `platform1/2/3`、`variantList` 这类命名**。
4. **AI 结果的 confidence 必须落到 UI**（§4.8）：`recognize.confidence` 里低于 0.7 的字段要在详情页**标黄并提示人工确认**。用户修改过的字段要写入 `edits` 数组（含 `isCorrection` 布尔标记），这是长期的评测数据来源，不能省。
5. **错误码统一**（§4.7）：不允许只有 happy path。401（访问码错误）、402（额度用尽）、413（图片超限）、415/400（格式错误）、5xx（上游异常）都要有明确 UI 状态。复用 `apps/mp/src/api.ts` 的 `apiErrorMessage()`，不要自己判断状态码。
6. **禁止的工作范围**（§1）：不要加登录、账号体系、多租户、支付、对象存储、Dockerfile、CI 配置。
7. **不得修改 `apps/mp/src/manifest.json` 里的 `appid`**：当前值是别人的/测试值，改了会污染 git 历史。

## 实现要求

1. **UI 风格对齐现有录入页**，不要另起一套视觉语言。
2. **详情页承载全部增值能力**：修正字段 → 生成卖货描述 → 生成三平台文案 → 长按复制文案。
3. **三平台文案生成是串行的三次模型调用**，耗时明显，UI 必须有明确等待态和进度提示（后端会按平台逐个推送 `generated` 事件）。
4. **详情页右上角展示额度余量**（`/api/runtime-info`），让使用者知道还剩多少。
5. TypeScript strict，**严禁 `any` 兜底**；`@ts-ignore` 必须旁边写明原因。
6. 标识符英文、**注释和提交信息用中文**；注释只写「为什么」，不要写「做了什么」。
