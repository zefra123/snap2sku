# snap2sku 单机部署手册

本手册适用于单台 Linux 服务器、本地持久化磁盘、systemd 和 Nginx。它描述试用部署步骤，不代表服务已经部署到线上。

## 开始前

准备一台有持久化磁盘的 Linux 服务器、已解析到该服务器的域名，以及模型服务商签发的 API Key。服务使用 SQLite 单写者模式，不要启动多个应用实例。请确认防火墙开放 SSH、HTTP 与 HTTPS，应用端口只监听回环地址。

仓库根目录 `package.json` 固定 `pnpm@11.19.0`；仓库锁定的 Nuxt 4.5.2 要求 Node `^22.19.0 || ^24.11.0 || >=26.0.0`，better-sqlite3 13.0.3 要求 Node `>=22`。建议选择 Node 22.19.0 或更高的 22.x 版本，并安装 pnpm 11.19.0。不要使用低于依赖要求的运行时。

### 环境准备（装依赖）

新建的 Ubuntu 机器通常只有 Node / git，下面几项要自己装：

```bash
# pnpm 必须与仓库 packageManager 一致
sudo npm i -g pnpm@11.19.0
pnpm --version          # 必须输出 11.19.0

sudo apt update
sudo apt install -y nginx sqlite3 curl
sudo apt install -y certbot python3-certbot-nginx
```

**先检查 80 端口有没有被占。** 腾讯云/阿里云的部分 Ubuntu 镜像会预装 Caddy 并在 `:80` 提供默认占位页，它和 Nginx 会直接抢端口：

```bash
sudo ss -tlnp | grep ':80 '
sudo systemctl disable --now caddy    # 看到 caddy 占用就停掉它
sudo systemctl enable --now nginx
```

预期：`ss` 只剩 nginx 监听 80。Caddy 在这里只是镜像自带的静态占位服务，停掉不影响 SSH 与控制台登录。

## 第 1 步：创建系统用户与目录

在服务器执行：

```bash
sudo useradd --system --home-dir /opt/snap2sku --shell /usr/sbin/nologin snap2sku
sudo install -d -o snap2sku -g snap2sku -m 0750 /opt/snap2sku/releases
sudo install -d -o snap2sku -g snap2sku -m 0750 /var/lib/snap2sku
sudo install -d -o root -g snap2sku -m 0750 /etc/snap2sku
```

预期：`/var/lib/snap2sku` 已存在并归 `snap2sku` 所有。**部署的第一步必须先创建数据目录**；生产程序发现目录不存在会拒绝启动，不会创建空账本。

`NUXT_DATA_DIR` 必须使用 Linux 绝对路径，例如 `/var/lib/snap2sku`。不要填写相对路径，也不要在 Windows/Git Bash 中把 `/var/...` 当作 Windows 盘符路径使用。上传图片位于 `$NUXT_DATA_DIR/uploads`；备份时要一并备份该目录。

## 第 2 步：准备发布目录并安装依赖

将代码检出到独立发布目录，以下 `<release-id>` 用本次 Git 提交短哈希替换：

```bash
sudo -u snap2sku git clone <仓库地址> /opt/snap2sku/releases/<release-id>
cd /opt/snap2sku/releases/<release-id>
node --version
pnpm --version
pnpm install --frozen-lockfile
```

预期：Node 版本满足前述依赖要求，pnpm 输出 `11.19.0`，安装完成且 lockfile 未被修改。仓库地址应使用服务器可访问的私有地址；不要把访问令牌写入命令历史。

## 第 3 步：构建并准备当前版本

在发布目录执行：

```bash
pnpm build
test -f apps/web/.output/server/index.mjs && ls -l apps/web/.output/server/index.mjs
```

预期：build 成功，`ls -l` 显示服务入口文件。创建当前版本软链接：

```bash
sudo ln -sfn /opt/snap2sku/releases/<release-id> /opt/snap2sku/current
```

## 第 4 步：配置环境变量与权限

复制模板并编辑：

```bash
sudo install -o snap2sku -g snap2sku -m 0600 deploy/env.example /etc/snap2sku/env
sudoedit /etc/snap2sku/env
sudo chown snap2sku:snap2sku /etc/snap2sku/env
sudo chmod 600 /etc/snap2sku/env
```

设置 `NUXT_ACCESS_CODE`、`NUXT_UPLOAD_SIGNING_SECRET`、`NUXT_VISION_API_KEY`、真实模型单价、`NUXT_TRIAL_RESERVE_CNY` 和唯一 `NUXT_TRIAL_ID`。上传签名密钥至少 32 字节，可在可信机器上生成：

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

将生成值安全地写入服务器环境文件。不要把真实密钥或域名提交到仓库。`NUXT_VISION_INPUT_PRICE_PER_MILLION` 和 `NUXT_VISION_OUTPUT_PRICE_PER_MILLION` 若为 0，费用估算恒为 0，预算熔断不会触发；必须从实际模型控制台复制真实单价，不能猜测。

## 第 5 步：安装并启动 systemd 服务

先核对 `deploy/snap2sku.service.template` 中的 `/opt/snap2sku/current` 和 `/var/lib/snap2sku` 与实际路径一致，再安装 unit：

```bash
sudo install -o root -g root -m 0644 /opt/snap2sku/current/deploy/snap2sku.service.template /etc/systemd/system/snap2sku.service
```

模板里的 `ExecStart` 默认写 `/usr/bin/node`，你的服务器未必是这个路径。先查真实路径并替换：

```bash
command -v node
sudo sed -i "s#^ExecStart=/usr/bin/node #ExecStart=$(command -v node) #" /etc/systemd/system/snap2sku.service
sudo systemctl daemon-reload
systemctl show -p ExecStart snap2sku
```

预期：`systemctl show` 输出的 `ExecStart` 指向真实存在的 node 可执行文件。不要使用 nvm 安装的 node：它位于用户家目录下，system 用户的 shell 是 `nologin`，读不到该路径，服务会报 `status=203/EXEC`。

预期：`/etc/systemd/system/snap2sku.service` 已安装。随后验证并启动：

```bash
sudo systemd-analyze verify /etc/systemd/system/snap2sku.service
sudo systemctl daemon-reload
sudo systemctl enable --now snap2sku
sudo systemctl status snap2sku --no-pager
sudo journalctl -u snap2sku -n 100 --no-pager
```

预期：unit 校验无错误，状态为 `active (running)`。日志应显示 `[store] 数据目录: /var/lib/snap2sku` 以及账本是沿用还是新建。控制进程：

```bash
sudo systemctl restart snap2sku
sudo systemctl status snap2sku --no-pager
sudo journalctl -u snap2sku -f
```

## 第 6 步：配置 Nginx 与 HTTPS

安装 `deploy/nginx.conf.example`，编辑并替换 `<你的域名>`，然后启用站点：

```bash
sudo install -o root -g root -m 0644 /opt/snap2sku/current/deploy/nginx.conf.example /etc/nginx/sites-available/snap2sku
sudoedit /etc/nginx/sites-available/snap2sku
sudo ln -s /etc/nginx/sites-available/snap2sku /etc/nginx/sites-enabled/snap2sku
```

如果启用链接已存在，先检查它是否指向该站点文件。检查配置并重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

先按 Certbot 官方 Nginx 指引安装 Certbot，并用 HTTP 验证域名解析和站点连通。随后申请证书：

```bash
sudo certbot --nginx -d <你的域名>
sudo certbot renew --dry-run
```

Certbot 会配置证书和续期任务；核对最终 Nginx 配置仍将请求转发到 `127.0.0.1:3000`。Nginx 模板明确设置 `proxy_buffering off`，让 SSE 增量及时到达；`/api/uploads/` 设置 `Cache-Control: private, max-age=60`，与签名 URL 的 60 秒有效期一致。上传限制为 `10m`，部署前要与前端压缩后的实际图片体积和服务端限制对齐。

## 第 7 步：检查服务

在服务器本机执行：

```bash
curl --fail --show-error https://<你的域名>/api/health
```

预期响应为：

```json
{ "status": "ok" }
```

该公开探针只返回健康状态。预算、Mock 和待对账信息通过带访问码的 `/api/runtime-info` 查询，不应添加到 `/api/health`。

## 备案等待期：用测试号做真机联调（可选）

域名备案未下号时，正式 AppID 走不通：小程序生产环境要求 HTTPS + 已备案域名，而这段时间**不能把域名解析到境内服务器**（见「常见问题」）。这条等待 Chain 常常要一两周，不必干等——用**测试号**可以现在就在真机上验证主流程。

### 为什么需要测试号

测试号是微信给开发者分配的临时账号，有自己的 AppID，可以额外跳过域名校验。代价是它**不能发布上线**，只能调试。所以它填的是「等待备案」这个窗口，不是替代正式账号。

|                       | 正式 AppID       | 测试号 AppID     |
| --------------------- | ---------------- | ---------------- |
| 真机预览              | 可以（域名受限） | 可以             |
| 跳过 HTTPS / 域名校验 | 不可以           | 可以             |
| 可配置服务器域名      | 可以             | **后台无此页面** |
| 提交审核、发布        | 可以             | **不可以**       |

### 第一步：申请测试号

测试号的申请入口**不在公众平台的任何菜单里**，这是很多人找不到的原因。直接访问这个地址，用微信扫码即得：

```
https://mp.weixin.qq.com/wxamp/sandbox?doc=1
```

扫码后会同时拿到小程序和小游戏两个测试账号，页面直接显示 AppID。登录后访问 mp.weixin.qq.com 扫码，在账号列表里选择对应的测试号进入。

### 第二步：临时替换 AppID

用微信开发者工具新建项目，填入测试号的 AppID。

如果是现有项目，改 `apps/mp/src/manifest.json` 的 `mp-weixin.appid`：

```json
{
  "mp-weixin": {
    "appid": "wx<测试号>",
    "setting": { "urlCheck": false }
  }
}
```

> **`appid` 所在的 `manifest.json` 没有被 gitignore，改动会进版本库。** 上线前必须改回正式 AppID；改回来之前不要执行 `git add apps/mp/src/manifest.json`，更不要用 `git add -A`。

`urlCheck: false` 等价于开发者工具里的「不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」，仓库里已经配好了，不需要改。

### 第三步：指向临时 Nginx

把小程序接口地址指到第 6 步之前的临时 Nginx（`deploy/nginx.staging.conf.example`，监听 8080 转发到本机 3000）：

```bash
cd apps/mp
# .env.local 写入的不是域名，而是公网 IP + 8080
echo 'VITE_API_BASE_URL=http://<公网IP>:8080' > .env.local
pnpm --filter mp build:mp-weixin
```

`.env.local` 已被 gitignore，可以放心改。安全组需要放行 8080，并且**不要放行 3000**。

### 第四步：真机调试

在开发者工具里点「预览」，手机扫码打开后，**点击右上角 ··· → 打开调试**。这一步不能省：真机上的域名校验是独立开关，只在开发者工具里勾选不够。

### 恢复正式 AppID

备案完成后回头执行第 8 步，并把 `manifest.json` 的 `appid` 改回正式 AppID。**这一步漏掉会直接导致上线失败**，而且 AppID 会留在 git 历史里。

> 另一半风险：`.env.production` 里如果写了正式域名，在这套联调里不要用它构建——它会让产物指向还未备案的 HTTPS 域名，而此时该域名尚未准备好。

### 测试号做不了的事

- 后台没有「服务器域名」配置页，一切域名配置都谈不上；
- 不能提交审核、不能发布，体验成员之外的用户看不到；
- 真机上的「打开调试」每次都要手动开。

## 第 8 步：构建与发布小程序端

前 7 步只覆盖 Web 服务。仓库根命令 `pnpm build` 等价于 `pnpm --filter @snap2sku/web build`，**不会构建小程序**。

先在微信公众平台 → 开发管理 → 开发设置 → 服务器域名，把你的 HTTPS 域名加入 **request 合法域名** 与 **uploadFile 合法域名**。小程序在生产环境只接受已备案的 HTTPS 域名；开发者工具里的「不校验合法域名」只对调试生效。

再在本地或构建机上注入接口地址后构建：

```bash
cd apps/mp
cp .env.example .env.local
# 编辑 .env.local，写入 VITE_API_BASE_URL=https://<你的域名>
pnpm --filter mp build:mp-weixin
ls dist/build/mp-weixin
```

预期：`dist/build/mp-weixin` 下有小程序产物。`.env.local` 已被 gitignore，不会进入仓库；不要把真实域名提交到 `.env.example`。

最后用微信开发者工具打开该目录，上传并提交审核。真机验证一次「拍照 → 识别 → 提交」，确认走的是线上域名而不是域名白名单校验。

## 升级与回滚

升级时在新的发布目录执行检出、`pnpm install --frozen-lockfile` 和 `pnpm build`，验证入口文件后再切换软链接并重启：

```bash
sudo ln -sfn /opt/snap2sku/releases/<new-release-id> /opt/snap2sku/current
sudo systemctl restart snap2sku
sudo systemctl status snap2sku --no-pager
sudo journalctl -u snap2sku -n 100 --no-pager
```

失败时切回上一个发布目录并重启：

```bash
sudo ln -sfn /opt/snap2sku/releases/<previous-release-id> /opt/snap2sku/current
sudo systemctl restart snap2sku
sudo systemctl status snap2sku --no-pager
```

升级前不要删除旧发布目录。数据库结构变更需先确认旧版代码兼容，不能通过切回代码恢复已迁移的数据。

## 备份与恢复

SQLite 使用 WAL 模式，**禁止用 `cp` 直接复制数据库文件**。运行 SQLite CLI 后使用一致性备份：

```bash
sudo install -d -o snap2sku -g snap2sku -m 0750 /var/backups/snap2sku
sudo -u snap2sku sqlite3 /var/lib/snap2sku/records.sqlite ".backup '/var/backups/snap2sku/records.sqlite'"
sudo -u snap2sku tar -C /var/lib/snap2sku -czf /var/backups/snap2sku/uploads-$(date +%F-%H%M%S).tar.gz uploads
```

若服务器未安装 SQLite CLI，先安装发行版提供的 `sqlite3` 命令行工具。也可在 SQLite 连接中使用 `VACUUM INTO` 生成一致性数据库副本。备份 `records.sqlite` 与 `$NUXT_DATA_DIR/uploads`，并将备份移至独立的持久化介质。恢复前停止服务，恢复数据库和 uploads，再启动并检查日志。本轮只定义备份方法；定期恢复演练在后续任务进行。

## 常见问题

- **服务启动失败**：先运行 `sudo systemctl status snap2sku --no-pager` 和 `sudo journalctl -u snap2sku -n 200 --no-pager`。检查 Node 版本、入口绝对路径、环境文件权限和目录所有权。
- **提示数据目录不存在**：确认 `/var/lib/snap2sku` 已预先创建且 `NUXT_DATA_DIR` 是 Linux 绝对路径；程序生产模式不会自动创建目录。
- **域名还没备案，能否先解析过去调试**：**不能。** 云厂商会周期扫描「域名 → 境内 IP」的解析关系，未备案域名一旦指向境内节点，常见后果是整台服务器的公网访问被暂停 24–72 小时，连 SSH 调试都受影响。这段时间只用 `http://<公网IP>:8080` 访问，域名保持不解析；域名一经注册就不管它，等备案通过再配。同理，备案未通过前也不要申请 HTTPS 证书——Certbot 的 HTTP-01 验证要求域名可解析且 80 端口可达，两个条件此时都不成立。
- **健康检查失败**：依次检查 `systemctl status`、应用 journald、`curl http://127.0.0.1:3000/api/health`、Nginx `error.log` 和 `nginx -t`。
- **API 返回 401**：受保护的请求需在 `x-access-code` 请求头携带与 `NUXT_ACCESS_CODE` 一致的值。`/api/health` 与签名图片读取接口 `/api/uploads/*` 不使用该访问码门禁。
- **SSE 内容一次性出现**：确认 Nginx 对上游设置 `proxy_buffering off`，并检查中间 CDN 是否缓冲响应。
- **预算数字始终为零**：确认真实单价已填入、Mock 已关闭，并带访问码请求 `/api/runtime-info`。

## 练习

1. 执行一次 `systemctl restart snap2sku`，从 journald 确认服务恢复且数据目录未改变。
2. 用访问码请求 `/api/runtime-info`，核对 `budget`、`spentCny` 与 `remainingCny`。
3. 在测试环境验证一次 SQLite `.backup` 和 uploads 压缩包均可读取；不要在本轮试用账本上做破坏性恢复测试。
