# 小程序功能扩展方案

## 结论

小程序端不需要开发任何新后端能力。**服务端已有的 6 个能力里有 4 个小程序完全没接**，把它们接上就是最划算的功能拓展——顺带把「单页面」这个驳回风险也解掉了。

## 现状盘点

小程序端目前只有一个页面（`pages/index/index.vue`，816 行），链路是：

```
选图 → 上传 → 识别 → 填写库存/吊牌价/批发价 → 提交
```

而服务端实际提供：

| 接口                                      | 能力                         | Web 端已接 | 小程序端 |
| ----------------------------------------- | ---------------------------- | ---------- | -------- |
| `POST /api/recognize`                     | 图片识别                     | 是         | 是       |
| `POST /api/records`                       | 保存记录                     | 是         | 是       |
| `GET /api/records`                        | 记录列表                     | 是         | **否**   |
| `PUT /api/records/:id`                    | 编辑记录                     | 是         | **否**   |
| `POST /api/records/:id/describe`          | 生成卖货描述                 | 是         | **否**   |
| `POST /api/records/:id/describe-variants` | 抖音/小红书/视频号三平台文案 | 是         | **否**   |
| `GET /api/runtime-info`                   | 额度余量                     | 是         | **否**   |

其中 **三平台文案变体**是整套系统里最有卖点的功能，Web 端做完了，小程序端一次都没调用过。这是白捡的功能。

`apps/web/app/pages/records.vue` 是现成的参考实现，字段、错误处理、SSE 流式呈现都写好了，照着改交互即可。

## 页面重构：1 页变 3 页

```
pages/index/index     录入页（现有瘦身，识别完直接跳详情）
pages/records/index   记录列表页（新增）
pages/detail/index    详情页（新增，含编辑与文案生成）
```

底部加两个 tabBar（录入 / 记录）会让页面层级一目了然，进一步降低「功能过于简单」的判定风险——审核规则 3.1.5 的原话就是「不能只有一个页面、只有一个按钮」。

详情页承担全部增值功能：**修正字段 → 一键生成卖货描述 → 一键生成三平台文案 → 长按复制**。

## 优先级

**P0（做这两页就够了）**

1. 记录列表页，接 `GET /api/records`
2. 详情页，接 `PUT` + `describe` + `describe-variants`

做完这两页：页面数 1 → 3，驳回风险解除，且多出一个能直接演示的完整闭环。

**P1（便宜且加分）**

3. 详情页展示额度余量（接 `/api/runtime-info`），让使用者知道 ¥200 还剩多少
4. 录入成功后直达详情页，形成完整闭环

**P2（先不做）**

5. 多图录入——上传接口支持 1–5 张，但改动面大
6. 历史搜索 / 分类筛选
7. 导出表格

## 已核实的安全结论

动手之前我逐条查了代码，这三条决定了方案能不能安全地做：

- **新增功能不会绕过 ¥200 熔断。** `describe` 与 `describe-variants` 底层都走 `vision.ts` 的 `reserveModelCall` + `runReservedModelCall`（`vision.ts:412` 和 `vision.ts:540`），和识别接口用的是同一套预占/结算机制，并且各自带一次重试。
- **列表页可以直接显示缩略图。** `records.get.ts` 返回的是经过 `addImageUrls` 处理的记录，每次拉列表都会签发新的签名 URL，不会撞上 60 秒过期。这正是当初 P0-2 修好的那个坑，列表场景天然不会出现。
- **三平台是串行生成的**，不会并发爆量，但一次生成耗时是三次模型调用，UI 必须给明确的等待态。

成本提醒：识别之外，每次「生成描述」和「生成三平台文案」都是**真实的模型调用、真花钱**。额度有限时优先保证识别能用。

## 技术要点与坑

1. **页面间只传 `id`，不要传 record 对象。** `uni.navigateTo` 的 url 有长度限制，把整个对象序列化进去既超限又难维护。详情页拿到 id 后自行拉详情。
2. **详情页的数据源。** 列表接口返回的是数组，详情页建议用列表数据兜底 + `PUT` 后回写，避免为了单条详情再加 `GET /api/records/:id`。
3. **SSE 流式响应。** `describe` / `describe-variants` 是 SSE（`generated` / `done` / `error` 事件），小程序端不能直接用 `uni.request` 的常规返回处理，要开 `enableChunked` 或者退化为一次性接收。参考 `apps/web/app/pages/records.vue` 的既有实现。
4. **`pages.json` 要同步改。** 新增页面必须写进 `pages` 数组；加 tabBar 还需要图标资源，图标要放在 `static/` 下而不能是远程地址。
5. **访问码只存本机。** 现有实现用 `uni.getStorageSync("snap2sku-access-code")`，详情页和新页面要沿用同一份读取逻辑，别各写一套。

## 不建议加的

- **登录 / 账号体系**：一旦有账号体系，就触发规则 3.3.4「需提供测试号，包含账号和密码」，还要做注销入口，成本远超收益。现在单一访问码的模式反而最适合提审。
- **支付相关**：个人主体办不了微信支付。
- **诱导分享、营销页**：规则 3.2.1 / 3.2.2 明确会拒。
