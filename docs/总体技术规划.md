## 1. 系统架构总览

```
                       ┌─────────────────────────────────────────┐
                       │              用户（服装商家）             │
                       └──────────────┬──────────────────────────┘
                                      │
              ┌───────────────────────┴───────────────────────┐
              │                                               │
     ┌────────▼────────┐                            ┌─────────▼─────────┐
     │  apps/web        │  浏览器                    │  apps/mobile       │
     │  Nuxt 4 + TS     │                            │  uniapp (Vue3)     │
     │  管理端（批量/表单）│                            │  W3 才开工（薄端）  │
     └────────┬─────────┘                            └─────────┬─────────┘
              │          都只调同一组 REST/SSE API               │
              └───────────────────────┬─────────────────────────┘
                                      │  /api/*
                       ┌──────────────▼──────────────────┐
                       │  apps/web/server（Nuxt server routes）│
                       │  ─ 后端 BFF 层，密钥只在这里 ─        │
                       ├──────────────────────────────────┤
                       │ /api/upload    图片落盘 + 元数据     │
                       │ /api/recognize 调 AI + zod 校验    │
                       │ /api/describe  SSE 流式文案        │
                       │ /api/records   录入记录 CRUD       │
                       └───────┬──────────────┬───────────┘
                               │              │
                    ┌──────────▼───┐   ┌──────▼───────────────┐
                    │ AI 适配器层    │   │ 存储层（演进式）        │
                    │ server/utils/ │   │ W1  data/records.json │
                    │ vision.ts     │   │ W2+ SQLite（见 §5）    │
                    │ GLM-4V-Flash  │   │ 图片: uploads/ → 对象存储│
                    │ ↕ 可换 Claude/ │   └──────────────────────┘
                    │   通义（同接口）│
                    └───────────────┘

     packages/shared    zod schema + 类型（前后端 + 双端唯一事实源）
     packages/prompts   识别/描述 prompt，独立版本化
```

**架构原则（每条都是决策，不是口号）**：

1. **没有独立后端服务**——Nuxt server routes 就是后端。单人 4 周，起第二个服务的运维成本 > 收益。代价是后端无法横向扩展，但 MVP 阶段单机够用（取舍记 README）。
2. **双端是"双壳一核"**——web 和 mobile 只做交互层，业务规则、类型、API 契约全部在 `packages/shared`，两端零业务逻辑复制。
3. **AI 是可替换零件**——所有模型调用收敛到 `server/utils/vision.ts` 适配器，业务代码只见接口不见 SDK。换模型 = 改一个文件 + 环境变量。
4. **存储是演进式的**——W1 用 JSON 文件是有意为之（先闭环再持久化），但数据访问必须从第一天就走 `server/utils/store.ts` 一个门面，JSON → SQLite 切换时业务代码零改动（见 §5）。

## 2. 前端规划

### 2.1 Web 管理端（apps/web，Nuxt 4 + TS）

| 页面/区域              | 内容                                                     | 里程碑                 |
| ---------------------- | -------------------------------------------------------- | ---------------------- |
| 录入工作台 `/`（主页） | 左 340px 上传队列 + 右侧表单 + SKU 矩阵 + 顶栏成本计数器 | W1                     |
| 记录列表 `/records`    | 单据风表格，行展开吊牌卡，耗时/成本/AI 标记              | W1（简版）→ W2（完整） |
| 描述生成区             | SSE 流式渲染，左缘靛蓝竖线，可编辑终值                   | W2                     |

**目录落位（Nuxt 4 实测约定）**：前端源码全在 `apps/web/app/` 下（`pages/`、`components/`、`composables/`、`assets/css/tokens.css`）；`server/`、`public/` 在 `apps/web/` 根下。别名 `~/`、`@/` → `app/`。

**状态管理**：先 `useState`（录入是一条流，状态集中）。W2 若记录列表 ↔ 工作台跨页共享变复杂，再评估 Pinia（待拍板项，不提前装）。

**性能考点（SKU 矩阵）**：颜色 × 尺码可达 500+ 输入框。策略：按行列分块渲染 + 非受控输入 + `font-variant-numeric: tabular-nums`。W1 Day 5 造 500 格基准，数字进 README。

### 2.2 移动端（apps/mobile，uniapp Vue3，W3）

- **定位薄端**：拍照 → 上传 → 预填确认 → 提交。批量管理、SKU 大矩阵编辑引导回 Web 端。
- 复用 `packages/shared` 的 schema 与 `packages/api` 的客户端（fetch 封装 + zod 运行时校验响应）。
- **兜底链**：小程序测试资质没有 / 时间爆了 → 降级 H5 移动适配，核心故事不变。
- W1/W2 期间**一个文件都不建**，只保证 shared 包的 API 设计不阻碍它（不依赖浏览器特有 API）。

## 3. 后端规划（apps/web/server）

### 3.1 API 全集（契约以 PRD 5.4 为准）

| 路由                 | 方法     | 职责                                                                                     | 错误码                                          | 里程碑 |
| -------------------- | -------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------- | ------ |
| `/api/upload`        | POST     | FormData 收图，文件头嗅探拒 HEIC，落盘 `uploads/`，返回 UploadFile                       | E_FORMAT / E_SIZE                               | W1     |
| `/api/recognize`     | POST     | 读图 → 适配器调 GLM-4V → 剥壳 → zod 校验（失败拼错误重试 1 次）→ RecognizeResult + usage | E_RECOGNIZE_INVALID / E_UPSTREAM / E_RATE_LIMIT | W1     |
| `/api/records`       | GET/POST | 记录读/写，POST 入参走 zod                                                               | E_VALIDATION                                    | W1     |
| `/api/describe`      | POST     | 确认字段 → SSE 流式描述，密钥不进 bundle                                                 | E_UPSTREAM                                      | W2     |
| `/api/records/batch` | GET      | 批量导入记录（W2 批量功能）                                                              | —                                               | W2     |

### 3.2 服务端结构

```
apps/web/server/
├─ api/                  # 路由层：参数校验 + 编排，不写业务细节
├─ utils/
│  ├─ vision.ts          # AI 适配器（唯一 import SDK 的地方）
│  ├─ store.ts           # 数据访问门面（JSON/SQLite 切换点）
│  └─ errors.ts          # 错误码 → HTTP 状态 + 用户文案的映射
└─ plugins/              # 启动时初始化（如 W2 的 db 连接）
```

**横切规则**：

- 密钥：`.env` + `runtimeConfig`（`NUXT_VISION_API_KEY/BASE_URL/MODEL`），只在 server 侧读。
- 限流：免费接口有并发限制，W1 串行请求，W2 加简单队列 + `E_RATE_LIMIT` 提示"排队中，第 N 位"。
- 所有响应先过 zod 再落盘/返回，不允许裸 `JSON.parse` 结果直传前端。

## 4. 数据模型（packages/shared，唯一事实源）

三个 schema 全部从 PRD 5.1–5.3 落地，此处不重复字段表：

- `RecognizeResult`：品类/颜色/风格/季节/人群/面料/品名/吊牌价（tagPrice，可 null）+ 逐字段 confidence
- `UploadFile`：fileId/体积对/mime（HEIC 拒收）
- `ProductRecord`：终值 + durationMs 三段埋点 + edits[] 修改流水 + aiCorrect 标记 + costEstimate + descriptionAi（描述编辑率口径）

**流转**：schema →（推导）→ TS 类型 → 表单枚举选项 → prompt 字段说明 → 响应校验。任何一处手写第二份 = bug。

## 5. 数据库与存储规划（演进式，核心是把切换成本压到零）

| 阶段                          | 记录存储                                          | 图片存储                                                  | 理由                                                        |
| ----------------------------- | ------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------- |
| **W1**                        | `data/records.json`                               | 本地 `uploads/`                                           | 先闭环。文件读写在 3 条记录/天的量级下毫无瓶颈              |
| **W2（2026-10-08 提前落地）** | **SQLite**（`better-sqlite3`，同步 API 简单可靠） | 本地，路径走门面                                          | 批量功能 + 记录量上来后需要查询/分页/事务；单机文件库零运维 |
| **W4 部署**                   | SQLite（同上）                                    | **对象存储**（如部署平台的 blob storage），路径抽象为 URL | server 跑在只读容器/多实例时本地文件会丢                    |

**实现细节（硬性，实测踩过/评估过的坑，不许省）**：

1. **JSON 阶段必须原子写 + 进程内写锁**：写临时文件再 `rename`（rename 是原子的），配一个互斥锁串行化"读→改→写"。不做的话：两个并发请求丢更新（开两个 tab 就能复现）；写到一半 crash 会把 `records.json` 写成半个 JSON，全量报废。
2. **SQLite 备份不许直接 `cp`**：拷到事务中间态 = 坏库。用 `better-sqlite3` 的 `.backup()` API，或 Litestream 流式备份（免费）。
3. **单实例部署是硬约束**：SQLite 单写者，起第二个 Node 实例写会坏数据。负载均衡/多实例要等切真正的 C/S 数据库（`store.ts` 门面就是为那天留的）。

**为什么切换不痛：`server/utils/store.ts` 门面**

```ts
// 业务代码只看这个接口，W1/W2 实现各一份
interface RecordStore {
  list(opts?: { page?: number }): Promise<ProductRecord[]>;
  save(record: ProductRecord): Promise<void>;
}
// W1: JsonFileStore（records.json 读写 + 防并发写锁）
// W2+: SqliteStore（建表见下）
```

**SQLite 表草案（W2 落地时照此建，字段与 zod schema 一一对应）**：

```sql
CREATE TABLE records (
  id TEXT PRIMARY KEY,
  created_at TEXT NOT NULL,           -- ISO
  duration_ms TEXT NOT NULL,         -- JSON {uploadStart,recognizedAt,submittedAt}
  images TEXT NOT NULL,              -- JSON fileId[]
  recognize TEXT NOT NULL,           -- JSON RecognizeResult（含 tagPrice）
  edits TEXT,                        -- JSON 修改流水
  ai_correct TEXT,                    -- JSON 评测标记
  cost_estimate REAL DEFAULT 0,
  description TEXT NOT NULL,          -- 终值
  description_ai TEXT                 -- AI 首次流式输出原文（描述编辑率口径）
);
CREATE TABLE skus (
  record_id TEXT NOT NULL REFERENCES records(id) ON DELETE CASCADE,
  color TEXT NOT NULL, size TEXT NOT NULL,
  stock INTEGER NOT NULL CHECK (stock >= 0),
  tag_price REAL NOT NULL CHECK (tag_price > 0),        -- 吊牌价（可预填 AI 建议值）
  wholesale_price REAL NOT NULL CHECK (wholesale_price > 0),  -- 批发单价
  PRIMARY KEY (record_id, color, size)
);
-- 字段名与 zod schema 一一对应：tagPrice→tag_price、wholesalePrice→wholesale_price
```

迁移：由 `store.ts` 初始化时检测并导入 `data/records.json`，事务成功后将原文件改名为 `data/records.json.bak`；重复启动不会重复导入。数据库备份必须调用 better-sqlite3 的 `.backup()` API，不得直接复制 SQLite 文件。

## 7. 不做的事（架构层面的边界）

- 不起独立后端服务（Nuxt server routes 扛住）
- 不上 PostgreSQL/MySQL/MongoDB（单机单人量级，SQLite 到顶再谈；选型对比已评估过，见 README 设计取舍）
- 不做 ORM 全家桶（drizzle/prisma 不进 W1-W2；better-sqlite3 手写 SQL + 类型由 zod 保证）
- 不做登录/多租户/缓存层/消息队列——PRD 明确"不在本期"

## 8. 上线安全基线（已拍板 2026-10-06）

> 背景：项目要公开上线，"无鉴权 + 公网可写"组合有三个真实风险——陌生人上传违规图片（合规责任在服务器所有者）、烧光免费 AI 额度、COS 存储账单无上限。

**方案：访问码门禁**（不是登录体系，不违反"不做登录"的范围纪律）：

- 实现：环境变量 `NUXT_ACCESS_CODE` + server middleware 校验 `x-access-code` 请求头。未配置时允许本地开发并设置 `X-Access-Code-Mode: disabled` 响应头；已配置时，缺失或错误的访问码返回 401。
- 范围：`/api/upload`、`/api/recognize`、`/api/describe`、`/api/records`（POST）全部要求；`/api/records`（GET）放行（Demo 可看不可写）。
- 兜底：即使有访问码，仍加每 IP 上传/识别频率限制（W2 随限流队列一起做）。
- 时机：已于 W2（2026-10-08）提前落地；部署前仍需设置正式访问码并验收所有写接口。
