# 小程序提审文案（个人主体）

本文案按**个人主体**设计，核心策略是把 snap2sku 定位成**图片识别工具**，而不是电商/交易工具。

原因来自微信官方运营答复，原文：

> 若你是个人主体小程序：名称应符合个人主体性质，不能涉及企业/单位名义、前置/专项审批相关领域、国家公共事务等关键字进行命名，**不得超出个人经营范围（如商城、商贸等）**。

规则依据：《微信小程序平台常见拒绝情形》。下面每一栏都注明了它规避的是哪条规则。

---

## 一、名称（不得含商城/商贸/批发/进货/开店）

**可用（任选其一，建议先查是否已被占用）：**

| 候选         | 说明                      |
| ------------ | ------------------------- |
| 拍图识款     | 首选，动词+名词，辨识度高 |
| 图转商品卡   | 描述性强                  |
| 商品图录助手 | 偏工具感，最保守          |
| 拍图填货号   | 略口语                    |

**禁用词**：商城、商贸、批发、进货、进销存、卖家、开店、入驻、交易、ERP、官网、官方、第一、最。

> 规则 1.2.1(3)：名称不能是单词汇，**必须是两个词以上的组合**。所以不要叫「录货」「识图」这种两字名。
> 另一个隐蔽的坑：2026 年有开发者反馈，名称里带 `App` / `Pro` 后缀也可能被要求改名。别加后缀。

---

## 二、简介（必须写明功能点，并包含名称里的词）

规则 1.2.1(1)(2)：简介不能用模糊表达（官方点名的反例是「提高用户的生活品味」），且**简介中必须能找到小程序名称或拆分出来的词**。

名称定为「拍图识款」时，复制这段（93 字）：

```
拍图识款是一款服饰图片识别工具：拍摄或从相册选取图片后，自动识别品类、颜色、风格、季节与适穿人群，并给出商品命名建议；支持手动修正识别结果，导出 SKU 数据用于个人整理存档。
```

换成其他名称时，把开头四个字替换掉，其余不变。

写法要点：

- 开头**重复一遍名称**，满足名称与简介的关联要求；
- 必须是**具体功能点罗列**，不能写「打造」「赋能」「提升体验」这类空话；
- 结尾「个人整理存档」把性质锚在自用工具上，对冲「电商」联想。

---

## 三、服务类目与标签

- **服务类目**：工具 → 效率 / 图像处理（以后台类目表为准）
- **服务范围**：必须与所选类目一致
- **服务标签**：识图、OCR、效率工具

> 规则 1.2.3：服务标签不能超出服务范围（官方反例：范围是家政、标签是美食）。

---

## 四、用户隐私保护指引（强制）

自 2023 年 9 月 15 日起，**未完成隐私指引配置的小程序无法通过审核**。

本项目实际调用的隐私接口只有两个，其余全部不勾选：

| 勾选的接口 | 填写的用途说明                   |
| ---------- | -------------------------------- |
| 摄像头     | 用于拍摄需要识别的商品图片       |
| 相册       | 用于从相册选取需要识别的商品图片 |

**关键区分**（官方社区答复原文）：

> 【相册（仅写入）权限】的用途是保存图片或保存视频，**是没有编辑个人信息、上传等功能的哦**。

本项目要**读取**相册并上传，所以勾的是「相册」而不是「相册（仅写入）」。勾错会被以「描述不明确」驳回。

不要勾：位置、手机号、通讯录、麦克风、用户信息。本项目一个都没用。

规则要求「针对不同的隐私接口分别详细描述」，所以两行必须分别写，不能合并成一句「用于上传图片」。

## 五、提审备注与测试账号（最容易被漏掉的一栏）

**这是驳回风险最高的一栏。** 小程序首页会先要求输入访问码，审核人员拿不到码就进不去任何功能，结果通常是直接驳回。

提交审核页面的填写方式：

- **测试账号**：`<填写你生成的 NUXT_ACCESS_CODE 原值>`
- **测试密码**：`无`（本项目没有密码体系，只有单字段访问码）
- **版本描述**（非必填，建议填）：

```
本小程序为自用图片识别工具，无账号体系。首页「访问码」输入框需填入测试账号栏提供的访问码，保存后即可使用全部功能：选择/拍摄图片 → 自动识别 → 修正结果 → 导出 SKU 数据。图片不会上传至任何第三方，仅用于本次识别。
```

规则 3.3.4 的原文是「若小程序中存在账号体系，需提供测试号，包含账号和密码」。本项目严格说没有账号体系，但**访问码的拦截效果等价**，所以照给。

另外注意规则 3.1.4：**审核人员必须能完整体验到所有功能**，不能有看着像付费/隐藏才能用的东西。

## 六、两个必须处理的驳回风险

### 风险 1：单页面可能被判「功能过于简单」

规则 3.1.5 原文：

> 小程序的功能应具有使用价值，不能过于简单，示例：只有一个页面，只有一个按钮。

本项目 `apps/mp/src/pages.json` 里只有一个页面 `pages/index/index`。虽然这一个页面内部功能完整（拍照、上传、识别、字段修正、SKU 表、文案生成），但审核看到的是「只有一个 page」。

**建议**：提审前改成多页面或至少加分包有明显页面层级——把「识别结果」和「历史记录」拆成独立页面。目前小程序端还没有记录列表页，这也是同一个风险。

### 风险 2：导航栏标题要改

`pages.json` 的 `navigationBarTitleText` 现在是 `snap2sku 商品录入`，既带英文又带「商品」二字。改成与名称一致：

```json
"navigationBarTitleText": "拍图识款"
```
